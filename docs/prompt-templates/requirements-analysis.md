## R-01 需求歧义和缺失分析

**场景**：需求评审会议前，从可测性角度系统性找出问题  
**推荐工具**：Kimi（长文档）  
**效果评级**：⭐⭐⭐⭐⭐  
**最后验证日期**：2026-07-20

```
你是一名资深测试架构师，擅长从可测性角度评审需求文档。
以下是需求描述：
[粘贴需求]
请从以下 4 个维度分析：
1. 模糊或矛盾的表述（至少 3 处）
2. 缺失的约束条件（范围/格式/类型限制未定义）
3. 缺失的异常处理说明（失败场景未定义）
4. 不可测的描述（无法验证的表述，如"系统应快速响应"）
输出：表格，列：问题编号 | 问题类型 | 原文引用 | 问题描述 | 建议补充的验收标准
```

## R-02 测试范围提取

**场景**：从需求文档提取完整测试范围（比自己看更全面）  
**推荐工具**：Kimi / 通义千问  
**效果评级**：⭐⭐⭐⭐⭐  
**最后验证日期**：2026-07-20

```
你是一名测试工程师。
以下是[功能名称]的完整需求描述：
[粘贴需求]
请提取测试范围，输出：
1. 功能测试点列表（每个业务规则一个测试点）
2. 非功能测试点（性能/安全/兼容性——标注是否需要专项）
3. 集成/数据流测试点（涉及其他系统或模块的边界）
4. 可能被忽略的灰色地带
格式：有序列表，每条一句话，标注优先级（高/中/低）。
```

## R-03 验收标准生成（Given-When-Then）

**场景**：为用户故事生成可直接使用的验收标准  
**推荐工具**：任意  
**效果评级**：⭐⭐⭐⭐⭐  
**最后验证日期**：2026-07-20

```
你是一名业务分析师，熟悉敏捷开发和用户故事写法。
以下是一个用户故事：
[用户故事原文]
请生成完整验收标准，格式：
Given [前置条件]
When [触发动作]
Then [预期结果]
要求：
- 正常场景至少 2 条
- 异常场景至少 2 条
- 边界条件至少 1 条
- 每条 AC 必须具体可测，禁止模糊描述
```

## R-04 测试计划框架生成

**场景**：快速生成测试计划大纲（节省 60% 的写计划时间）  
**推荐工具**：Kimi / 通义千问  
**效果评级**：⭐⭐⭐⭐  
**最后验证日期**：2026-07-20  
**已知局限**：资源估算和风险部分需要根据团队实际情况大幅调整

```
你是一名测试管理专家。
项目信息：
- 功能描述：[简要描述]
- 开发周期：[N 周]
- 团队规模：[N 名测试工程师]
- 技术栈：[前端/后端/数据库]
- 已有自动化覆盖率：[约 N%]
请生成测试计划大纲，包含：
1. 测试范围（In Scope / Out of Scope）
2. 测试策略（功能/回归/API/性能/安全，标注是否需要）
3. 环境需求
4. 资源估算（参考，需按实际调整）
5. 时间计划（里程碑节点）
6. 风险识别（至少 3 个 + 应对策略）
7. 退出标准
格式：Markdown，使用标题和表格
```

## R-05 测试工作量估算

**场景**：为 Sprint 测试工作估算人天，辅助排期  
**推荐工具**：DeepSeek  
**效果评级**：⭐⭐⭐  
**最后验证日期**：2026-07-20  
**已知局限**：估算值通常偏低，建议 × 1.3 作为实际计划

```
你是一名有 10 年经验的测试 Lead，擅长工作量估算。
测试范围：[描述功能模块和主要测试场景]
已有信息：
- 自动化覆盖率目标：[N]%
- 已有自动化框架：[是/否，框架名]
- 团队配置：[N 手工测试 + N 自动化工程师]
请估算：
1. 手工测试工时（用例设计/执行/Bug 验证/回归）
2. 自动化脚本工时（如适用）
3. 总工时 + 建议预留的 Buffer（%）
4. 主要估算假设（哪些假设影响最大）
注意：这是参考估算，最终需结合团队实际调整。
```

## R-06 需求评审邮件生成

**场景**：将评审发现的问题整理为发给 PO 的正式确认邮件  
**推荐工具**：Kimi / 通义千问  
**效果评级**：⭐⭐⭐⭐  
**最后验证日期**：2026-07-20

```
请将以下需求问题清单整理成一封发给产品经理（PO）的确认邮件。
问题清单：[粘贴 R-01 的输出]
需要 PO 在 [日期] 前回复，以便测试团队准时开始用例设计。
要求：
- 专业但友好的语气，不要显得在"挑刺"
- 按"影响测试设计/影响开发/需要 PO 决策"分组
- 每个问题说明为什么需要确认（影响是什么）
- 结尾写明等待回复的 Deadline 和后续计划
```
