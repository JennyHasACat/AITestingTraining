# M4 测验 — Bug 分析与报告规范化

> **题目数量**：8 题 | **建议时间**：10 分钟 | **通过标准**：6 题正确

---

## 选择题（单选，每题 1 分）

**Q1. 以下哪条 Bug 报告标题写得最规范？**

- A. 支付有问题
- B. 点击支付按钮后系统报错
- C. 【结账模块】选择信用卡支付后点击"确认支付"，页面白屏且无错误提示
- D. BUG：支付功能在某些情况下会失败，需要修复

<details markdown="1">
<summary>查看答案</summary>

**答案：C**

解析：规范的 Bug 标题格式为"[模块名] + [操作] + [错误现象]"。C 明确了模块（结账）、操作（选择信用卡 + 点击确认支付）、现象（白屏 + 无错误提示），开发人员看标题就知道在哪、做什么、出了什么问题。

</details>

**Q2. 发现一个 Playwright 测试报 `StaleElementReferenceException`，最可能的原因是什么？**

- A. 网络超时，页面加载太慢
- B. 元素在操作前已被 DOM 替换或页面重新渲染，之前获取的元素引用已失效
- C. 元素存在但被其他元素遮挡，无法点击
- D. 选择器语法错误，无法找到元素

<details markdown="1">
<summary>查看答案</summary>

**答案：B**

解析：`StaleElementReferenceException` 的直接含义是"元素引用已过时"——在获取元素和操作元素之间，页面发生了 DOM 更新（如 AJAX 刷新、Vue/React 重渲染），导致之前保存的元素引用不再有效。

</details>

**Q3. 以下哪种情况应该被标记为 P0 Critical？**

- A. 商品描述页面有一个错别字
- B. 移动端界面在小屏幕上布局有轻微错位
- C. 所有用户无法完成注册（注册按钮点击无效）
- D. 导出报告的 Excel 文件，数字格式显示为文本

<details markdown="1">
<summary>查看答案</summary>

**答案：C**

解析：P0 Critical 的定义是"主流程无法执行，无绕过方法"。注册功能完全失效会影响所有新用户，是典型的阻断性问题。A 是 P3，B 是 P2，D 是 P2/P1（取决于使用频率）。

</details>

---

**Q4. 当你把一段 `TimeoutError` 日志发给 AI 分析时，除了报错信息本身，还应该提供哪些关键信息？**

- A. 只需要错误类型名称即可
- B. 框架版本、选择器内容、操作前的页面状态
- C. 完整的测试脚本代码（所有行）
- D. 测试运行服务器的 CPU 使用率

<details markdown="1">
<summary>查看答案</summary>

**答案：B**

解析：对于 TimeoutError，AI 最需要的信息是：框架版本（不同框架等待机制不同）、失败的选择器（帮助判断选择器是否可能错误）、页面状态（帮助判断元素是否应该存在）。完整代码通常不必要且可能涉及敏感信息；CPU 使用率与此无关。

</details>

## 判断题（T/F，每题 1 分）

**Q5. Bug 报告中的"预期结果"应该描述"你认为系统应该怎样"，而不是"需求文档中写了什么"。**

<details markdown="1">
<summary>查看答案</summary>

**答案：F（错误）**

解析：预期结果应该基于**需求文档、规格说明或验收标准**，而不是个人主观判断。"我认为应该怎样"和"需求要求怎样"可能不一致。基于需求的预期结果更有说服力，也减少与开发的争议。

</details>

---

**Q6. 使用 AI 分析 Bug 时，Chain-of-Thought（要求 AI 分步推理）比直接问"这是什么问题"能获得更有用的分析。**

<details markdown="1">
<summary>查看答案</summary>

**答案：T（正确）**

解析：Chain-of-Thought 强制 AI 在给出结论前先展开推理步骤，这让 AI 能系统性地考虑多种原因，而不是只给出第一个想到的猜测。分步推理的中间过程也便于人工判断哪一步的假设可能有误。

</details>

## 简答题（每题 2 分）

**Q7. 以下是一条 Bug 报告的"复现步骤"，请指出它的问题并改写：**

原始复现步骤：
```
1. 打开系统
2. 进行操作
3. 出现错误
```

<details markdown="1">
<summary>参考答案</summary>

**问题**（1分）：复现步骤极度模糊，没有任何具体操作描述，开发人员完全无法独立复现。

**改写示例**（1分，以登录失败为例）：
```
前置条件：
- 测试账号：test@company.com（已注册，密码正确）
- 环境：Staging / Chrome 125

复现步骤：
1. 打开 https://staging.system.com/login
2. 在邮箱字段输入：test@company.com
3. 在密码字段输入 3 次错误密码（任意错误密码，如 "wrongpass123"）
4. 等待 30 分钟（账号锁定期）
5. 输入正确密码，点击"登录"
预期：账号解锁后，正确密码可以登录成功
实际：系统提示"账号不存在"，而不是预期的"账号已解锁，登录成功"
```

</details>

**Q8. 你发现了一个 Bug：某个下拉字段在选择特定值后，后面的条件字段没有出现（在手动测试中可以复现）。请写出你给 AI 分析时应该提供的完整上下文信息（列出至少 4 项关键信息）。**

<details markdown="1">
<summary>参考答案</summary>

需要提供的关键信息（每项 0.5 分，答出 4 项给满分）：

1. **触发条件**：下拉字段的名称 + 选择的具体值（如 "contractType" 选了 "NonPromoter"）
2. **预期出现的字段**：条件字段的名称/功能描述（如 "weeklyHours" 应该在选择 Part-time 后显示）
3. **实际现象**：字段完全不显示、显示后隐藏、还是显示但不可交互？
4. **环境信息**：浏览器 + 版本 + 测试环境（Staging/UAT）
5. **复现率**：每次都复现，还是偶发？
6. **历史状态**：这个功能之前是好的吗？是最近部署后出现的？
7. **相关业务规则**：什么条件触发字段显示（如果知道的话）

</details>
