## Lab 2-B：Few-shot 格式对齐练习（15 min）

### 目标

你的团队有一套 Bug 报告模板，让 AI 学习后批量生成同风格报告。

### 步骤

1. 选取你们团队中一份真实的 Bug 报告（或使用下方示例）
2. 将其作为 Few-shot 示例，然后要求 AI 基于新的场景描述，生成相同格式的 Bug 报告

**示例 Bug 报告（可替换为真实案例）**：
```
标题：搜索框输入超过 50 字符时页面崩溃
严重程度：P0
复现率：100%
环境：Chrome 125 / Windows 11 / Staging
前置条件：已登录普通用户账号，进入商品搜索页
复现步骤：
  1. 在搜索框输入 51 个字符的字符串
  2. 点击搜索按钮
预期结果：系统提示"搜索关键词长度不能超过50字符"
实际结果：页面白屏，控制台报 TypeError: Cannot read property 'slice' of undefined
附件：[截图链接]
```

**你的 Prompt**（将示例嵌入后发给 AI）：
```
以下是我们团队的标准 Bug 报告格式：
[粘贴上面的示例]

请按完全相同的格式，为以下场景写一份 Bug 报告：
场景：用户在注册页面，密码字段输入了包含中文字符的密码（如"密码123"），
提交后系统没有报错，但实际登录时该密码无法使用。
```

## Lab 2-C：Chain-of-Thought 复杂分析练习（20 min）

### 场景

你收到了以下测试失败日志（模拟真实场景）：

```
FAILED tests/test_user_creation.py::test_create_user_with_duplicate_email
E  AssertionError: assert 200 == 400
E  + where 200 = <Response [200]>.status_code
AssertionError: Expected status 400 (Bad Request) for duplicate email,
but got 200 (OK). Response body: {"id": 1043, "email": "test@example.com", "status": "created"}
```

### 步骤

**第一次**（不用 Chain-of-Thought），直接发：
```
以上日志代表什么问题？
```

记录输出质量：__________

---

**第二次**（使用 Chain-of-Thought），发送：
```
你是一名资深后端测试工程师。
以下是一个 API 测试的失败日志：
[粘贴上面的日志]

请按步骤分析：
第1步：识别断言失败的直接原因（预期值 vs 实际值的差异）
第2步：列出 3 个可能的根本原因（后端未校验重复邮箱 / 测试数据未清理 / 接口路由错误等），按可能性排序
第3步：为每个假设给出最快验证方法（1–2 行操作步骤）
第4步：如果你是 SDET，你会优先检查哪里？给出建议
```

记录输出质量：__________

---

**对比问题**：
1. 两次回答的结构和深度有什么差别？
2. 思维链方式是否给出了你没想到的排查方向？
