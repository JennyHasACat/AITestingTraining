# M5 测验 — 需求评审 + 测试计划提效

## 选择题（单选，每题 1 分）

**Q1. 测试团队参与需求评审的最大价值是什么？**

- A. 帮助开发团队提前写代码
- B. 在最低成本阶段发现需求缺陷，避免后期返工
- C. 替代业务分析师（BA）撰写用户故事
- D. 确保所有需求都在一个迭代内实现

<details markdown="1">
<summary>查看答案</summary>

**答案：B**

解析：缺陷发现越早，修复成本越低。需求阶段发现问题只需修改文档，测试阶段发现需要重新开发和测试，生产阶段发现代价最高。测试人员的"怀疑眼光"是需求评审中的独特价值。

</details>

---

**Q2. Given-When-Then 格式的验收标准中，"Then" 部分应该描述什么？**

- A. 触发业务规则所需的前置条件
- B. 用户执行的操作步骤
- C. 系统在特定操作后的可观测预期行为
- D. 开发实现的技术方案

<details markdown="1">
<summary>查看答案</summary>

**答案：C**

解析：Given（前置条件）→ When（触发动作）→ Then（预期结果）。"Then" 描述的是系统应该表现出的可观测行为，必须具体可验证（如"页面显示成功提示"而非"系统运行正常"）。

</details>

---

**Q3. 以下哪条需求描述是"不可测的"，需要在评审时要求澄清？**

- A. 用户名长度不能超过 20 个字符
- B. 支付超时时间为 30 秒
- C. 系统应该提供良好的用户体验
- D. 密码必须包含至少一个大写字母

<details markdown="1">
<summary>查看答案</summary>

**答案：C**

解析："良好的用户体验"无法测量，没有明确的通过/失败标准。A、B、D 都有具体可量化的验证标准。遇到这类模糊需求时，测试团队应要求 PO 给出可测的验收标准（如：关键页面加载时间 < 2 秒）。

</details>

---

**Q4. 用 AI 辅助需求评审后，输出的"问题清单"应该如何处理？**

- A. 直接作为测试用例使用
- B. 整理后在需求评审会议上与 PO 确认，等待回复后再开始用例设计
- C. 保存在本地，不需要与开发/PO 共享
- D. 把所有问题都自动标记为 Bug 提交

<details markdown="1">
<summary>查看答案</summary>

**答案：B**

解析：AI 发现的需求问题是"潜在疑点"，需要与产品经理（PO）确认后才能确定是真正的问题。擅自假设答案会导致测试方向偏差。问题清单应整理后正式沟通，并在开始用例设计前得到确认。

</details>

## 判断题（T/F，每题 1 分）

**Q5. AI 生成的测试计划可以直接用于项目执行，无需人工修改。**

<details markdown="1">
<summary>查看答案</summary>

**答案：F（错误）**

解析：AI 生成的测试计划是"通用框架"，不了解你的项目历史、团队技能、现有自动化覆盖率、公司流程要求等特定约束。必须人工根据实际情况调整，特别是资源估算和风险部分。

</details>

---

**Q6. 在 AI 辅助需求评审中，使用 R-02（测试范围提取）比 R-01（歧义分析）更重要，应该优先做 R-02。**

<details markdown="1">
<summary>查看答案</summary>

**答案：F（错误）**

解析：R-01（歧义分析）应该优先于 R-02（范围提取）。如果需求本身存在歧义或缺失，基于模糊需求提取的测试范围也是不准确的。正确顺序：先澄清需求 → 再提取测试范围。

</details>

---

**Q7. 使用 R-07 绘制准入漏斗时，如果 L1 系统准入层的鉴权校验失败，AI 应继续生成该请求在 L2 和 L3 的业务规则执行结果。**

<details markdown="1">
<summary>查看答案</summary>

**答案：F（错误）**

解析：R-07 的漏斗必须体现逻辑短路。L1 未通过时，请求已被系统拦截，L2 业务准入和 L3 分支/算法不应执行。测试路径应验证拦截结果，而非假设后续逻辑仍会发生。

</details>

## 简答题（每题 2 分）

**Q8. 以下需求描述有 3 处缺陷，请逐一指出：**

```
"用户可以上传头像，支持常见图片格式，文件不能太大，
上传成功后用户界面会更新显示新头像。"
```

<details markdown="1">
<summary>参考答案</summary>

三处缺陷（各 0.67 分）：

1. **"常见图片格式"未定义**：到底支持哪些格式？JPG/PNG/GIF/WebP/SVG？需要明确列出支持和不支持的格式。

2. **"文件不能太大"未量化**：最大文件大小是多少？100KB？1MB？5MB？不同大小对应什么提示？

3. **"用户界面会更新"不可测**：是立即更新（同步）还是需要刷新页面？更新的范围是什么（只是头像区域还是所有使用头像的地方）？

</details>

---

**Q9. 请为以下用户故事写出 3 条 Given-When-Then 格式的验收标准（覆盖正常、异常各至少 1 条）：**

```
用户故事：作为用户，我希望能重置我的密码，以便在忘记密码时找回账号访问权限。
```

<details markdown="1">
<summary>参考答案</summary>

示例（各 0.67 分）：

**AC1（正常场景）**：
```
Given 用户在登录页面点击"忘记密码"
When 用户输入已注册的邮箱地址并点击"发送重置链接"
Then 系统在 30 秒内向该邮箱发送重置链接邮件，页面显示"重置链接已发送，请查看邮箱"
```

**AC2（正常场景）**：
```
Given 用户收到重置链接并在 24 小时内点击
When 用户输入新密码（满足复杂度要求）并确认
Then 密码更新成功，用户被跳转到登录页，原密码失效
```

**AC3（异常场景）**：
```
Given 用户在"忘记密码"页面
When 用户输入系统中不存在的邮箱地址
Then 系统显示"如果该邮箱已注册，你将收到重置邮件"（不泄露邮箱是否存在）
```

（评分要点：格式正确、覆盖正常和异常、预期结果具体可验证）

</details>
