# M5 实战 Lab — OmniPeople 定制版：New Hire 需求评审

> **预计时长**：35 分钟 | **工具**：Kimi（长文档分析推荐）

---

## Lab 5-A：OmniPeople New Hire 需求评审（15 min）

### 背景

以下是一段模拟的 OmniPeople New Hire 功能需求描述（基于真实业务逻辑整理，已脱敏）：

```
新员工入职流程需求说明（v2.3）

1. Manager 可在 Manager Service 模块发起新员工入职申请
2. 员工类型分为：全职（Full-time）和兼职（Part-time）
3. 全职员工：需填写薪资级别、职位、合同类型
4. 兼职员工：需额外填写预计每周工时
5. 合同类型包括：Standard、NonPromoter、Promoter、RedBook
6. 不同合同类型对应不同的字段组合（由系统自动控制显示）
7. 入职日期不能早于提交日期
8. 审批通过后，员工信息自动同步到 HR 系统
9. 若信息填写有误，审批人可"退回"申请，由 Manager 修改后重新提交
```

### 步骤

使用 **模板 R-01** 分析上面的需求，特别关注：
- 合同类型字段组合的具体规则未定义
- "不能早于提交日期"的边界未精确定义（当天是否可以？）
- "退回"后的重新提交是否有次数限制？
- 同步失败的处理机制

## Lab 5-B：Given-When-Then AC 生成（10 min）

选择以下其中一个用户故事，生成完整 AC：

**选项 A（全职员工）**：
```
作为一名 Manager，
我希望能为新员工选择正确的合同类型，
以便确保入职流程符合公司的雇佣规定。
```

**选项 B（兼职员工）**：
```
作为一名 Manager，
我希望为兼职员工指定预计每周工时，
以便 HR 系统能正确计算薪资。
```

用 **模板 R-03** 生成 AC，然后检查：
- AC 是否覆盖了你在 Lab 5-A 中识别的问题点？
- 有没有针对"不同合同类型字段显示"的 AC？

## Lab 5-C：测试工作量估算（10 min）

基于你在 Lab 5-A 和 Lab 5-B 中识别的测试范围，使用 **模板 R-05** 估算：

```
功能范围：New Hire 入职申请流程（含全职/兼职/4种合同类型）
自动化状态：已有 Playwright 框架，部分场景已自动化（约 40% 覆盖率）
目标：本迭代新增场景的测试工时估算
团队：2 名测试工程师（1名手工，1名自动化）
```

**注意**：在 Prompt 中告知 AI 团队已有自动化基础，让它区分"手工测试工时"和"新增自动化工时"。
