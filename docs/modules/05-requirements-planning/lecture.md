# M5 — 需求评审 + 测试计划提效

> **时长**：1.5 小时 | **受众**：全员必修 | **前置要求**：M1 + M2 完成

---

## 学习目标

完成本模块后，你能够：
1. 用 AI 从需求文档中快速提取测试范围和测试点
2. 使用 AI 识别需求中的歧义、缺失约束和矛盾点
3. 借助 AI 生成测试计划框架，减少从零撰写的时间
4. 用 AI 估算测试工作量（用于项目排期）
5. 将 AI 辅助需求评审成果整理为可复用的团队资产

---

## 第一节：需求评审的测试视角（15 min）

### 为什么测试团队要参与需求评审？

```
发现问题的成本（越早越便宜）：
需求阶段 × 1  →  开发阶段 × 6  →  测试阶段 × 15  →  生产阶段 × 100
```

测试工程师在需求评审中的独特价值：
- 从"用户会怎么用错"的角度挑刺
- 识别不可测的需求（"系统应该运行流畅"→ 如何验证？）
- 发现遗漏的边界条件和异常场景
- 提前预判测试难点和风险

### AI 在这个环节的价值

| 任务 | 无 AI | 有 AI |
|------|-------|-------|
| 读懂需求 | 反复阅读，凭经验找问题 | AI 快速扫描，输出问题清单 |
| 提取测试点 | 手动逐行整理 | AI 系统性提取，秒级完成 |
| 撰写测试计划 | 从模板开始逐字填写 | AI 生成框架，人工补充细节 |
| 工作量估算 | 拍脑袋或查历史数据 | AI 给参考基线，结合经验调整 |

## 第二节：需求评审 Prompt 模板（30 min）

### 模板 R-01：需求歧义和缺失分析

```
你是一名资深测试架构师，擅长从可测性角度评审需求文档。
以下是一段需求描述：
[粘贴需求]

请从以下 4 个维度分析，找出问题：
1. 模糊或矛盾的表述（AI 不确定、人也可能理解不一致的地方）
2. 缺失的约束条件（什么值是有效的？有范围限制吗？）
3. 缺失的异常处理说明（如果 X 失败，系统怎么处理？）
4. 不可测的描述（"系统应快速响应"类——无法验证的描述）

输出格式：
| 问题编号 | 问题类型 | 原文引用 | 问题描述 | 建议补充的验收标准 |
```

---

### 模板 R-02：测试范围提取

```
你是一名测试工程师。
以下是[功能名称]的完整需求描述：
[粘贴需求]

请提取测试范围，输出：
1. 功能测试点列表（每个业务规则对应一个测试点）
2. 非功能测试点（性能、安全、兼容性——标注是否需要专项测试）
3. 集成/数据流测试点（涉及其他系统或模块的边界）
4. 可能被忽略的灰色地带（需求未明确说明但实际需要验证的点）

格式：有序列表，每条一句话，标注优先级（高/中/低）
```

---

### 模板 R-03：验收标准生成（AC Generation）

```
你是一名业务分析师，熟悉敏捷开发和用户故事写法。
以下是一个用户故事：
[用户故事原文]

请为这个用户故事生成完整的验收标准（AC），格式使用 Given-When-Then：
Given [前置条件]
When [触发动作]
Then [预期结果]

要求：
- 覆盖正常场景（至少 2 条）
- 覆盖异常场景（至少 2 条）
- 覆盖边界条件（至少 1 条）
- 每条 AC 必须具体可测，不允许模糊描述
```

## 第三节：测试计划 AI 生成（20 min）

### 什么是测试计划？

测试计划回答 5 个问题：
1. **测什么**（范围）
2. **怎么测**（策略和方法）
3. **谁来测**（资源分配）
4. **什么时候测**（时间计划）
5. **有什么风险**（风险和应对）

### 模板 R-04：测试计划框架生成

```
你是一名测试管理专家，擅长制定测试计划。
项目信息：
- 项目名称：[项目名]
- 功能描述：[简要描述]
- 开发周期：[N 周]
- 团队规模：[N 名测试工程师]
- 技术栈：[前端/后端/数据库]

请生成一份测试计划大纲，包含：
1. 测试范围（In Scope / Out of Scope）
2. 测试策略（功能测试/回归/API/性能/安全——标注是否需要）
3. 测试环境（建议的环境配置）
4. 资源估算（建议每个阶段的人天数）
5. 时间计划（里程碑节点）
6. 风险识别（至少 3 个风险 + 应对策略）
7. 退出标准（什么条件下可以发布）

格式：Markdown，使用标题和表格
```

## 第四节：工作量估算 Prompt（10 min）

### 模板 R-05：测试工作量估算

```
你是一名有 10 年经验的测试 Lead，擅长测试工作量估算。
以下是一个功能模块的测试范围：
[粘贴测试维度清单或功能描述]

历史参考数据（如果有）：
- 上个模块大小：[N 个功能点]，实际测试工时：[N 人天]
- 自动化覆盖率目标：[N]%

请估算：
1. 手动测试工时（包含：用例设计/执行/Bug 验证/回归）
2. 自动化脚本开发工时（如适用）
3. 总工时建议
4. 主要估算假设（哪些假设影响最大）
5. 风险系数（建议预留多少 buffer）

注意：这只是参考估算，最终数据需要结合团队实际情况调整。
```

---

## 第五节：需求评审输出整理（10 min）

完成 AI 辅助需求评审后，将输出整理为可用于会议的格式：

```
请将上面的需求问题清单整理成一封邮件，
发给产品经理（PO）确认。
格式要求：
- 专业但友好的语气
- 每个问题按"影响测试/影响开发/需要 PO 决策"分组
- 结尾写明需要 PO 在[日期]前回复，以便测试团队准时开始用例设计
```
