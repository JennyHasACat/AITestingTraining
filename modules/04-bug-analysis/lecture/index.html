    M4 — Bug 分析与报告规范化¶

    时长：1.5 小时 | 受众：全员必修 | 前置要求：M1 + M2 完成

    学习目标¶

    完成本模块后，你能够： 1. 用 AI 从原始报错日志快速提炼根因假设列表 2. 使用 Chain-of-Thought 模式进行结构化 Bug 分析 3. 借助 AI 将口头描述 / 零散记录转化为规范 Bug 报告 4. 将 AI 生成的 Bug 描述调整为符合团队规范的格式 5. 用 AI 辅助进行缺陷优先级和严重程度判断

    第一节：AI 在 Bug 分析中的价值（15 min）¶

    没有 AI 时的典型流程¶

    看到报错 → 凭经验猜原因 → 尝试复现 → 反复查资料 → 找开发沟通
平均时间：30分钟 ~ 2小时

    有 AI 辅助的流程¶

    把报错 + 上下文给 AI → AI 生成结构化根因假设列表 → 
按优先级验证假设 → 快速定位 → 写规范 Bug 报告
平均时间：5分钟分析 + 2分钟写报告

    AI 在 Bug 分析中最擅长的事¶

    场景 AI 的价值
    常见错误类型识别 NullPointerException / TimeoutError / StaleElementReference 等模式匹配
    可能原因枚举 系统性列出假设，避免遗漏明显原因
    验证思路建议 告诉你最快的验证方法（查哪个日志/加什么断言）
    报告规范化 将口头描述整理为结构化格式
    跨模块影响分析 基于错误描述推断可能的影响范围

    第二节：Bug 根因分析 Prompt 模板（25 min）¶

    模板 B-01：日志分析¶

    你是一名资深 SDET，擅长 [Python/Java/JavaScript] 调试和日志分析。
以下是一段测试运行时的报错信息：

[粘贴完整报错日志，包括 traceback]

环境信息：
- 测试框架：[Playwright/pytest/Selenium]
- 语言/版本：[Python 3.11]
- 浏览器：[Chromium 125]

请按以下步骤分析：
1. 识别报错类型和触发位置（文件名 + 行号）
2. 列出 3 个最可能的根本原因，按可能性从高到低排序
3. 每个假设给出最快验证方法（1–2 步操作）
4. 给出最终修复建议

    模板 B-02：UI 测试失败分析¶

    你是一名 Playwright 自动化测试专家。
以下是一个 UI 测试失败的场景：

测试名称：[test_xxx]
失败步骤：[在哪一步出错]
报错信息：[错误类型和消息]
截图/页面状态：[描述页面当前状态]

请分析：
1. 这个错误最可能是什么原因（选择器失效/元素未加载/超时/数据问题/环境问题）
2. 如何用最少步骤验证你的假设
3. 如果是选择器问题，推荐什么更稳健的选择器策略
4. 建议的修复方向（修改定位器/增加等待/数据准备）

    模板 B-03：API 测试失败分析¶

    你是一名 API 测试专家。
以下是一个 API 测试失败的信息：

请求：[METHOD] [URL]
请求体：[Request Body（脱敏后）]
期望响应：[状态码 + 关键字段]
实际响应：[状态码 + 响应体]

请分析：
1. 直接原因（哪个字段不符合预期）
2. 可能的后端原因（校验逻辑/数据库/权限/中间件）
3. 如何用最快方式定位问题（调试端点/查日志/检查测试数据）
4. 如果这是一个真实 Bug，建议的 Bug 报告严重程度是什么？理由？

    第三节：AI 辅助撰写规范 Bug 报告（20 min）¶

    为什么 Bug 报告质量很重要？¶

    • 低质量报告 → 开发无法复现 → 来回沟通 → 浪费双方时间
    • 高质量报告 → 开发直接定位 → 快速修复 → 测试效率提升

    Bug 报告标准结构¶

    标题：[操作] + [条件] + [错误现象]（一句话，清晰无歧义）
严重程度：P0/P1/P2/P3
复现率：100% / 50% / 偶发
环境：浏览器版本 / OS / 测试环境
前置条件：执行测试前系统的状态
复现步骤：有序列表，具体操作
预期结果：根据需求/规格，应该发生什么
实际结果：实际发生了什么（具体！）
附件：截图 / 日志 / 录屏链接

    Prompt 模板 B-04：Bug 报告生成¶

    你是一名测试工程师，需要填写一份规范的 Bug 报告。
以下是我对这个 Bug 的口头描述：
[用自然语言描述你发现的 Bug，可以不完整]

环境：[测试环境信息]
严重程度（你的判断）：[P0/P1/P2/P3]

请帮我生成一份完整的 Bug 报告，包含：
标题、严重程度、复现率、环境、前置条件、复现步骤、预期结果、实际结果。
要求：
- 标题格式：[模块名] + [操作] + [错误现象]
- 复现步骤必须具体，能让没有上下文的开发人员独立复现
- 预期结果和实际结果的描述都必须具体可观测

    模板 B-06：Jira 缺陷创建与校验¶

    B-04 解决“把零散信息写成一份可读的 Bug 报告”；当团队还需要将报告映射到 Jira 的项目字段、校验 Description 完整性并条件创建 Issue 时，使用 B-06。

    原始 Bug 描述
   ↓
配置 Jira 项目字段（Project / Issue Type / Priority / Labels / Assignee 等）
   ↓
生成 Summary 和 Description
   ↓
检查 Description 是否包含 Steps、Expect Result、Actual Result
   ↓
客户端具备已授权 Jira 工具？
  是 → 创建 Issue 并返回 Key / 链接
  否 → 返回完整字段，人工创建

    使用 B-06 时，项目 Key、字段名、默认优先级、标签和标题格式都必须从输入配置读取，不能写死在 Prompt 中。信息不完整时填 NA 或标记“待补充”，不能编造复现步骤或需求预期。

    自动创建不是绕过评审的快捷方式：提交前仍要检查可复现性、重复 Issue、敏感数据和预期结果依据。Jira 工具不可用、无权限或创建失败时，AI 必须返回完整的人工录入字段，且未获得 Issue Key 前不能声称创建成功。

    第四节：Bug 严重程度与优先级判断（10 min）¶

    AI 辅助决策 Prompt¶

    以下是一个 Bug 的描述：
[Bug 描述]

请帮我判断：
1. 严重程度（Critical/Major/Minor/Trivial）的建议，并说明理由
2. 优先级（P0/P1/P2/P3）的建议，考虑：
   - 影响用户数量（核心流程 vs 边缘场景）
   - 是否有绕过方法
   - 修复难度（选项：高/中/低）
3. 如果这个 Bug 不在本迭代修复，会有什么业务风险？

    严重程度快速参考表¶

    严重程度 定义 示例
    P0 Critical 主流程无法执行，无绕过方法 无法登录系统
    P1 Major 核心功能受损，有绕过方法 提交表单失败但刷新后可重试
    P2 Minor 功能受影响但可使用 某字段显示格式错误
    P3 Trivial UI/文案/样式小问题 按钮颜色与设计稿不符

    第五节：常见自动化测试报错速查（10 min）¶

    报错类型 常见原因 AI 分析时要提供的信息
    TimeoutError: Timeout 30000ms exceeded 元素未出现/页面未加载/选择器错误 选择器内容 + 页面截图描述
    StaleElementReferenceException 元素在操作前页面已刷新/重渲染 操作前后的页面状态
    ElementNotInteractableException 元素被遮挡/隐藏/禁用 HTML 结构描述
    AssertionError 预期值与实际值不符 预期值 + 实际值 + 断言代码
    ConnectionRefusedError 测试环境未启动/URL 错误 环境 URL + 网络状态

    第六节：AI 提效小工具 —— 自动生成 Bug（10 min）¶

    待补充：具体工具 / 链接 / 进阶用法（由维护者持续更新）

    它解决什么问题¶

    测试失败时，人工整理 Bug 卡（标题、复现步骤、环境、日志归类）很费时。本工具思路是从失败日志 / 截图描述自动产出结构化 Bug 卡，直接可提交。

    核心思路（伪步骤）¶

    1. 输入：测试失败日志 / 报错信息 / 截图文字描述 / 环境信息
2. 工具内部：套用 B-01~B-04 的分析与报告 Prompt，必要时使用 B-06 映射 Jira 字段
3. 输出：规范 Bug 卡（标题 + 严重程度 + 复现步骤 + 预期/实际）或已校验的 Jira 字段

    提示词骨架（可直接复用）：

    你是资深 SDET。基于以下失败信息生成一份规范 Bug 报告：
- 失败日志：[粘贴 traceback]
- 环境：[浏览器 / OS / 测试框架]
- 截图描述：[页面状态]
请输出：标题（[模块]+[操作]+[现象]）、严重程度、复现率、复现步骤、预期结果、实际结果。
若能从日志推断根因，在报告末尾附"疑似根因"供开发参考。

    注意事项¶

    • 自动生成的"疑似根因"仅作参考，提交前建议人工确认；
    • 涉及生产数据 / 敏感信息的日志必须先脱敏。
    • 自动创建依赖 AI 客户端已授权的 Jira 工具；工具或权限不可用时，应输出完整字段供人工创建，不能伪造创建成功结果。

    本模块小结¶

    场景 使用的 Prompt 模板
    分析报错日志 B-01（日志分析）
    UI 测试失败 B-02（UI 失败分析）
    API 测试失败 B-03（API 失败分析）
    撰写 Bug 报告 B-04（Bug 报告生成）
    映射 Jira 字段并条件创建 B-06（Jira 缺陷创建与校验）
    判断严重程度 优先级判断 Prompt
